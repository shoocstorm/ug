# Session summary — 2026-07-27

One commit (`6f45988`) plus a small follow-up working tree, +3.3k / −241,
concentrated in `native/src/indexer/languages/java.rs` and
`native/src/graph.rs`.

The session started as a question — *what would most improve indexing, graph
and RAG quality for Java repos?* — and the answer turned out to be that the
Java indexer had never been more than the Python indexer with Java node kinds
pointed at it. That is fine for a language where a file path is an identity
and a symbol name is nearly unique within it. Java is neither. Three things
followed from that, and they had to be done in order because each one is the
input to the next.

---

## The chain

    package is never read
        -> no qualified names
            -> `import com.example.svc.OrderService;` resolves against the
               *filesystem*, finds no directory called `com.example.svc`,
               drops the edge
            -> the file-to-file import layer of every Java graph is empty
            -> and `save` / `execute` / `handle` identify nothing, so every
               call edge is a guess between all of them

    receiver is discarded at the call site
        -> `orderRepo.save(x)` and `auditLog.save(x)` both record `"save"`
            -> resolution falls back to "first registered id", preferring
               the caller's own file
            -> a controller calling `service.cancel(id)` links to *itself*

    annotations are not parsed at all
        -> what a class is for, which URL reaches a method, which table a
           type maps to — none of it is anywhere in the index
            -> "where is the endpoint that cancels an order" cannot be
               answered, because `/api/orders/{id}` is in no identifier, no
               path and no Javadoc

## 1. Qualified names

`java.rs` now reads `package_declaration` and maintains a type stack while
walking. Every symbol gets two names:

| | display (`Symbol.name`) | key (`Symbol.qualified_name`) |
|---|---|---|
| type | `OrderService`, `Outer.Inner` | `com.example.svc.OrderService` |
| method | `OrderService.cancel` | `com.example.svc.OrderService#cancel` |
| constructor | `Order.Order` | `com.example.model.Order#<init>` |
| field | `Order.id` | `com.example.model.Order#id` |

Both are load-bearing and they are deliberately different. The key has to be
exact, because the graph builder resolves against it. The display name has to
be *readable*, because it is what gets embedded and shown — and
`OrderService.cancel` splits into four searchable words where `cancel` gives
one.

Constructors are keyed `<init>` so `new Order(...)` at a call site resolves by
qualified name like any other call, while still displaying as something a
reader would search for.

`graph.rs` gained a `QualifiedIndex` holding, per repo: member key -> node
ids with their arities, type key -> node id, package -> its types, node ->
its file, and both directions of the type hierarchy. Imports, supertypes and
calls all resolve through it, with the old bare-name resolver kept as the
fallback.

Members are additionally nested under their declaring type with a `Contains`
edge. The file edge is kept as well — plenty of consumers walk file -> symbol
— but the class level is the one Java actually organises code at.

### Type resolution is local, and deliberately guesses outward

One file's imports, its own declarations, its package. No classpath, no
second pass. The resolution order follows Java's own with one deviation: the
current package is tried *before* on-demand (`.*`) imports. Getting that
backwards qualifies a same-package `Order` as `java.util.Order` — losing an
edge between two types that are really in the graph. This way round qualifies
`List` as `com.example.List`, which matches nothing, which is exactly what a
JDK type should do.

## 2. Receiver types

A new `CallRef { name, owner_type, argc }` rides alongside the existing
`calls: Vec<String>`, which keeps its old contract (deduped bare names, for
display and for the other languages' resolution path).

The indexer builds a per-method environment from class fields, record
components, parameters and locals — recorded as they are met, with no block
scoping. Receivers resolve for `this`, `super`, a variable in scope, a
capitalised bare identifier (a static call, by convention), `this.field`, and
a scoped identifier. Anything else — a chained call, a lambda parameter —
stays `None` and falls back to name matching.

Then, in the graph builder:

- **`Overrides` edges.** A method redeclaring an inherited signature points at
  the declaration it replaces. `Implements` is type-level and stops at the
  class, so before this "who implements this interface method" had no answer.
- **Dispatch fan-out.** A call typed against an interface is also drawn to the
  implementations, transitively, capped at 8. This is the whole ballgame for a
  codebase wired by dependency injection: the service only ever names the
  interface, so without it there is no path from a caller to any code that
  runs. It needs no DI-specific code — an `@Autowired OrderRepository repo`
  field is just a field whose declared type is known.
- **Supertype walk** (depth 8) so an inherited method resolves.

When a symbol has `call_refs`, `calls` is deliberately *not* also walked: it
holds the same call sites stripped of their receivers, and resolving those by
name is precisely the guesswork this replaces.

## 3. Annotations

Parsed from the `modifiers` child, stored as `{name, args}` with the package
qualifier stripped (`Test`, not `org.junit.Test` — that is how they are
written and searched for). Then used three ways.

**Retrieval text** (`storage/text.rs`). Two tables — one for annotations whose
meaning is in the name, one for annotations whose meaning is in an argument —
render into the prose someone would actually type:

    @Repository                 -> "Spring data access repository"
    @Entity @Table(name="orders") -> "JPA persistent entity. mapped to table orders"
    @Transactional              -> "runs in a database transaction"
    @KafkaListener(topics="…")  -> "consumes Kafka topic order-events"

Unrecognised annotations are still named and word-split, so a house
`@AuditLogged` contributes `AuditLogged (audit logged)`. `@Override` is the
one exclusion: it is on a large share of all methods, distinguishes none of
them, and the graph now records the same fact precisely as an edge.

Unlike the structural synopsis, these are *not* a fallback — they are added
whether or not the symbol has a docstring, because they say what a symbol
**is** in a way its prose usually assumes rather than states.

**Routes.** Type-level and member-level mapping annotations compose into
`GET /api/orders/{id}` (Spring's `@RequestMapping` family and JAX-RS `@Path` +
verb markers). It lands on `Symbol.route`, in the embedding text, and as a
`Route` node of its own with `file -> route` (Contains) and
`route -> handler` (References). A route is the name the outside world knows
the code by; it deserves to be a node.

**Classification.** `@Test` and friends identify a test whatever the layout.

## Measured, before and after

Same synthetic Spring project (controller -> service -> interface repo -> JPA
impl -> entity), `HEAD` in a scratch worktree vs. the new build:

| | before | after |
|---|---|---|
| `Imports` edges | **0** | 6 |
| `Calls` edges | 6 | 9 |
| `Overrides` | — | 2 |
| `Route` nodes | — | 2 |

The counts undersell it. The call edges before:

    OrderController.cancel  ->  OrderController.cancel     <- self-loop
    OrderController.find    ->  OrderController.find       <- self-loop
    OrderService.cancel     ->  OrderRepository.findById
    OrderService.cancel     ->  Order.markCancelled
    OrderService.cancel     ->  OrderRepository.save
    OrderService.find       ->  OrderRepository.findById

`service.cancel(id)` resolved to the controller's *own* `cancel`, because
`pick_best` prefers a same-file name match. Two of six were self-loops; the
rest were right only because nothing collided. After:

    OrderController.cancel -> OrderService.cancel
    OrderController.find   -> OrderService.find
    OrderService.cancel    -> OrderRepository.findById      (interface)
    OrderService.cancel    -> JpaOrderRepository.findById   (impl, via fan-out)
    OrderService.cancel    -> Order.markCancelled
    OrderService.cancel    -> OrderRepository.save
    OrderService.cancel    -> JpaOrderRepository.save
    OrderService.find      -> OrderRepository.findById
    OrderService.find      -> JpaOrderRepository.findById

## The four things that were not about Java

Each of these was found while working on the above, and each is a bug for
every language.

**`is_ignored_path` matched substrings of the whole path.** `IGNORED_DIRS`
held `node_modules`, `.git`, `target`, and any path merely *containing* one of
those strings was dropped — `src/targeting/`, `src/node_modules_helper.ts`.
Now compared per path component.

**`target` was ignored unconditionally**, which is right for Maven and Cargo
and wrong for Java, where `target` is a legal package name:
`src/main/java/com/acme/target/` and every class in it vanished from the
index. `target`/`build`/`out` are now skipped only when the build descriptor
that produces them (`pom.xml`, `Cargo.toml`, `build.gradle`) sits in the same
directory — applied as a walker `filter_entry`, so a match prunes the whole
subtree and the probe runs once per directory rather than once per file.

**The incremental cache keyed only on file content.** Exactly right for
detecting edits, exactly wrong for detecting a change to the *indexer*: after
an extractor gains a capability, every unchanged file is a cache hit and keeps
its old, poorer symbols forever. `cache.json` now carries
`__ug_indexer_version__`; a mismatch discards the cache whole. Bump
`INDEXER_VERSION` on any change to what the extractors produce, or the
improvement never reaches an existing install.

**Javadoc was read by the shared JSDoc extractor**, which scans a fixed
200-byte window backwards from the node — so it truncated any real Javadoc
and, on an annotated declaration, usually found only the annotations. It also
split `@param` on the first `-`, a TypeScript convention Javadoc doesn't use,
discarding every parameter description. Java now walks the previous sibling
comment node and flattens the block tags properly.

## The classifier, and a regression caught by a question

`src/test/java/com/example/service/OrderServiceTest.java` classified as
`Service` — the same label as the class it tests — because the only rule that
saw it was the `/service/` directory heuristic. Added: Maven/Gradle layout,
JUnit naming, `@Test` annotations, and JVM build descriptors as `Config`.

The first cut applied the JUnit naming conventions (`*Test`, `*Tests`, `*IT`,
`Test*`) to **every** language. `TestimonialCard.tsx` -> `Test`. `Testable.ts`
-> `Test`. Both are ordinary source, and mislabelling them makes them read as
test scaffolding in every type-filtered search.

The naming rules are now gated on `.java`, with a test pinning it. The
path rule (`/src/test/`) stays language-agnostic on purpose — a `src/test/`
directory means the same thing whatever is inside it — and the annotation rule
has no such failure mode.

The lesson generalises: a heuristic borrowed from one language's conventions
needs an explicit reason to apply outside it. `.test.` / `.spec.` earned that;
`Test*` did not.

## Wiring the new types through

`GraphNodeType::Route` and `GraphEdgeType::Overrides` needed registering in
`storage/types_registry.rs` — without it they persist to OverGraph as
`Unknown` (99 / 199) and no type filter ever finds them. IDs append at the
end and must never be renumbered.

Also: `overrides` added to `USAGE_EDGE_TYPES`, so `find_usages` on an
interface method surfaces its implementations — which is the most useful
possible answer to "what depends on this"; `Overrides` added to
`EDGE_TYPE_VOCABULARY`; and a colour, radius and icon for `Route` plus a
relation colour for `Overrides` in `visualization.html`.

## Blast radius

Every new resolution path is gated on `Symbol.qualified_name`, which only
`java.rs` sets. For a TS/Python/Rust repo `QualifiedIndex` stays empty and
every branch short-circuits — verified by self-indexing this repo (2032 nodes,
4806 edges): zero `Route` nodes, zero `Overrides` edges, counts otherwise
unchanged.

The new `Symbol` fields are generic, not Java-specific, and both `graph.rs`
and `text.rs` consume them without knowing the language. Two adjacent wins are
now cheap:

- **Rust** already qualifies methods as `Db::upsert_nodes`. Setting
  `qualified_name` + `owner` in `rust.rs` buys class -> member nesting and
  trait-method `Overrides` with no new graph code.
- **TypeScript decorators** are the same shape as Java annotations, and
  `ROLE_ANNOTATIONS` already holds names NestJS and Angular use
  (`@Controller`, `@Injectable`, `@Component`, `@Repository`). Extracting
  decorators in `typescript.rs` would give NestJS `@Get('/orders/:id')` route
  nodes through the existing path; the mapping table would need NestJS's
  spellings.

- **`java.rs` unit tests (20)** — extraction: qualified names, nesting,
  receiver typing, static imports, route composition, Javadoc, overload
  arity, annotation-argument parsing.
- **`tests/java_indexer_test.rs` (19)** — everything that is *cross-file*, and

  stage a real multi-file project into a `TempDir`.
- **`text.rs` (7)** — that the semantics reach the embedding text, survive
  alongside a docstring, and change nothing for a node without annotations.

Note for anyone writing more of the integration tests: `index()` names file
nodes by their path relative to the *canonicalised* repo root, and on macOS a
`TempDir` under `/var` canonicalises to `/private/var`, so the prefix never
strips and file node names come out absolute. The helper matches them by
suffix.

## Unrelated fix — the export buttons

`Uncaught ReferenceError: downloadGraph is not defined`, and the same for
`downloadIndex`, on every click of the two buttons in the Export tool panel.

Pre-existing, and a pure scope bug: the whole page lives in one
`<script type="module">`, module scope is not global scope, and an inline
`onclick="downloadGraph()"` attribute resolves against `window` — where the
function has never been. They were the last two inline handlers on the page;
everything else already wires through `addEventListener`. Now they do too.

Verified in headless Chrome against the mocked-API serve (see
`verify-ug-frontend-headless`): both buttons fire, produce `index.json` and
`graph.json`, zero console errors, zero `[onclick]` attributes remaining.

## Loose ends

- `docs/samples/java.graph.json` is stale-format. Nothing in the repo or the
  tests reads it and the source it was generated from is gone, so it was left
  rather than replaced with something invented.
- Anonymous-class methods are attributed to the enclosing type. Pre-existing
  behaviour, unchanged, and it double-counts their calls — the enclosing
  method already collected them.
- `OrderController.java` and `OrderRepository.java` still classify as `None`.
  `FileClassification` has no controller or repository variant, and adding one
  ripples further than this session's scope.
- Overload selection prefers an exact arity match and otherwise takes the
  first declaration, so a call through a varargs signature resolves to
  *something* rather than dropping. Real overload resolution needs types.
