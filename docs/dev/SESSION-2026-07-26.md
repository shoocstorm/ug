# Session summary — 2026-07-26

Two commits (`eb22e40`, `5bfbaaf`) plus a staged working tree of 23 files,
+1.7k / −273. Almost all of it under `native/src/storage/`.

The session started as a UI tweak to the KB Manager card and turned into a
question that reshaped the storage layer: *why is re-indexing slow when it
claims to be incremental?* It wasn't incremental. Chasing that produced a
chain where each answer exposed the next problem, and the fixes only made
sense in order.

---

## The chain

Re-index was slow because **nothing about it was incremental**. The comment in
`visualization.html` said `ug gen` skipped unchanged files via a blake3 cache;
the cache existed but was gated behind a `-c` flag the server never passed. And
even with it, the cache only covered *parsing* — ingest re-embedded all ~5,900
nodes on every run regardless.

Fixing embedding exposed that **node ids embedded the start line**, so any edit
made every symbol below it look brand new: re-embedded, and its old row orphaned
forever. Fixing ids made **pruning** safe for the first time. And storing code —
asked for so an agent could stop depending on the working tree — turned out to
also be what made the "body changed but description didn't" case cheap.

---

## 1. Incremental ingest

`ingest::plan_incremental_ingest` diffs the incoming graph against the store
before anything is embedded, sorting each node into three buckets:

| bucket | condition | embed | write |
| --- | --- | --- | --- |
| unchanged | stored row identical | no | no |
| reusable | `node_text` unchanged, another column moved | no | yes, carrying the stored vector |
| to embed | new, or `node_text` changed | yes | yes |

Two non-obvious things this had to get right:

**The id cache.** Skipping writes for unchanged nodes means nothing populates
`key_to_id` for them — and the *edge* upsert that follows resolves endpoints
through exactly that cache. The planner `remember`s every row it reads. There's
a regression test pinning it.

**Multi-destination.** The plan is built against one store, so it passes
`always_write` and every row still reaches every backend. Planning against one
and skipping writes on all would let a destination silently drift.

`nodes_for_upsert` was added to `KnowledgeStore` rather than reusing
`nodes_by_ids`, because OverGraph keys nodes by `(type_id, key)`: with the type
in hand it does one keyed read per node instead of `lookup_id`'s probe across
all ten type ids — and ingest always runs in a fresh process with a cold cache.
It later moved to OverGraph's batch `get_nodes_by_keys`, one round-trip per
2048-node chunk. The default impl delegates to `nodes_by_ids`, which is right
for Neo4j (already one `UNWIND`).

Measured, 278 nodes: **3.23 s → 0.11 s** with nothing changed; embedding
3.07 s → 7.6 ms on a one-function edit.

## 2. Parse cache on by default

`ug gen` now caches parsing in the project dir unless told otherwise;
precedence `--no-cache` → `-c/--cache` → output dir. The KB Manager gets it for
free because it shells out to `ug gen`.

Guard added beyond the plan: the cache is bypassed when `project.json` records a
different `ug` version. `indexed-tree.json` holds parsed `FileNode`s, so an
indexer change between releases would otherwise keep serving old-shaped nodes
for every file whose content happened not to change.

Parse stage: **20.1 ms → 2.9 ms** on a 16-file repo.

## 3. Line-independent node ids

`{kind}:{file}:{name}`, with `#N` appended on collision in source order
(`graph.rs::symbol_node_ids`). Both passes of `build_graph` call the one
function instead of duplicating a format string.

The measurement that settled the design: on a real 1,618-node graph, only
**1.30% of symbols** collide without the line number, because names already
arrive qualified (`Db::upsert_nodes`, not `upsert_nodes`). The collisions are a
recognisable class — a method in both an inherent and a trait `impl`, several
`From` impls.

Rejected: content-hash ids (they'd change exactly when a body is edited, making
every edit read as delete+insert — the opposite of what's wanted) and full
qualified names via container tracking (`Symbol` has no parent field, so it
would mean touching every language extractor for a 1.3% gain).

Line shift on one file went from **24 re-embeds + 24 orphans** to **24 vector
reuses, 0 embeds, 0 orphans**.

## 4. Pruning

`prune_nodes_absent_from` on the trait; real implementations for OverGraph
(per-type sweep, `ALL_NODE_TYPE_IDS` so adding a type can't leave a sweep
missing it) and Neo4j (`DETACH DELETE` anti-join — a default no-op would have
been a silent divergence between backends).

It refuses to run on an empty graph: ingest upserts a *complete* index, so an
empty node list means indexing produced nothing, not that the repo is empty.
Default-on for `ug gen` (`--no-prune`), opt-in for `ug ingest` (`--prune`),
since fanning several graphs into one store is legitimate there.

## 5. Stored source

`code` + `file_hash` columns on `NodeRow`, captured per **file** at ingest
(`storage::source`) — the naive per-node shape re-reads a whole file for every
symbol in it.

The argument for it, which is not really about speed: the store was a *pointer
index*. It could say where code lived but never what it said, so every read went
back to the working tree. Two consequences — the row's description and the code
an agent read could disagree, and a line range that had merely drifted still
*resolved*, silently handing back the wrong lines with no error.

Retrieval prefers the stored copy (`query::snippet_for`,
`agent_tools::get_code_with_stored`, tour), falling back to the filesystem for
legacy rows. `get_code` marks a slice `stale` when the file no longer matches
`file_hash`, so out-of-date source is reported rather than served as current.

Verified by deleting the source tree and re-querying: identical ranking,
snippets intact. **Search and `get_code` now work with no working tree at all.**

Cost, measured: captured spans came to **1.04x** the raw source — nesting
overlap is negligible because extractors give class nodes narrow declaration
ranges — and the source is *smaller than the dense vectors already in the same
database*. DB 7.2M → 8.4M for 1,692 nodes.

## 6. Sparse vectors — a dead code path

`Db::upsert_nodes` was writing `sparse_vector: None` for every node while
`hybrid_search` dutifully built one from the query. The keyword half of hybrid
search had been **matching against nothing**, and fusion silently degenerated to
dense-only.

Now built at ingest from `node_text` (weight 1.0) + `code` (0.35), capped at 512
dimensions. Code is discounted rather than equal-weighted because bodies dwarf
descriptive text and this tokenizer has no IDF to suppress `let`/`self`/`return`.
Neo4j's fulltext index gained `n.code` — caveat: `IF NOT EXISTS` will not widen
an existing index, so pre-existing Neo4j DBs need it dropped and recreated.

## 7. What goes into the embedding text

Two measurements reframed this. **47% of nodes** carry neither a docstring nor
a signature — their text was a bare `"Function: name. . Related: …"`. And the
median `node_text` used **6% of the 512-token window**. The constraint was never
budget; it was signal.

Three additions, all of which fill that room:

- **Identifier splitting** (`split_identifier`) — camelCase, snake_case and
  acronym runs (`parseXMLDocument` → `parse xml document`), used in both the
  embedding text and the sparse tokenizer so query and ingest agree by
  construction. The exact identifier stays first so exact-name queries still
  match verbatim.
- **Structural synthesis** (`synthesize_code_synopsis`) — the code counterpart
  of the existing folder synopsis. Contributes the file path, which is real
  prose signal that appeared nowhere in the text before. `calls` is deliberately
  excluded: `Related:` already names those neighbours, and call lists churn on
  every body edit.
- **Inline comments** (`storage::comments`) — run over the already-captured span,
  so no extra I/O and no per-language parser. Filters commented-out code (symbol
  density, code-like endings), tool directives (`eslint-disable`, shebangs), and
  separators; repeated licence banners are indexed once per graph. Only nodes
  with a real line range participate — a File node's span is the whole file, so
  it would otherwise absorb every comment and starve its symbols via the dedup.

**Source code is still not embedded densely**, deliberately. It would defeat
incremental re-ingest (a `cargo fmt` run would re-embed the repo), ~10% of
function bodies exceed the 512-token window and fastembed truncates them
silently, and body tokens dilute the docstring/name signal. Code belongs in the
sparse index and the stored column.

## What the measurements changed

Worth recording, because in three places the data contradicted a plausible
prior:

- **camelCase was not unreachable.** The stated reason for identifier splitting
  was that prose queries couldn't reach camelCase names. They could —
  bge-small's BPE already subword-splits them, and exact-word queries scored 8/8
  *before* the change. The real gain is narrower: paraphrase queries went
  10/12 → 12/12 on a purpose-built fixture. Directional, small sample.
- **Storing code was expected to bloat the DB.** It came to 1.04x source, less
  than the vectors already there.
- **Duplication from nesting was expected to be severe.** It isn't, because
  class nodes carry narrow ranges.

# Part 2 — documents, caps, and BM25

Commits `5977cf2`, `e15902c`, `79d99cc`. Tests **242 → 272**; clippy 51 → 49
warnings. Two new modules: `limits.rs`, `storage/sparse_stats.rs`.

Part 1 made indexing incremental and gave the store its own copy of the source.
Part 2 started from a report that a markdown node's embedded text read

```
Concept: Why bother with a local backend?. . Related: Embedding Backends
```

— and ended up rewriting how the embedding budget is decided and how the
keyword channel is scored. The same shape as Part 1: each fix exposed the next
problem, and the order matters.

## The chain

Markdown headings were indexed with **no docstring**, so a section's entire
prose reached the dense vector nowhere; only the heading's own words could
retrieve it. Fixing that raised the question of *how much* prose to embed —
which turned out to be a property of the **model**, not of markdown, and the
indexer runs before any embedder exists. Moving that cap to embed stage made it
derivable from the model's token window, which made **switching models** a
supported operation, which exposed that switching models silently mixed two
embedding spaces in one store. And having finally documented that the keyword
channel carried the corpus's prose, it became untenable that the channel had no
IDF: raw term frequency was fine for identifier queries and wrong for the
natural-language ones documents now attract.

## 8. Markdown embedded its headings, not its content

`section_prose` (`languages/markdown.rs`) attaches a heading's prose as the
symbol's `docstring`, which flows through the existing `node_description`
docstring branch into `node_text`. Same shape `document.rs` already used for PDF
pages — the two document pipelines were inconsistent, not uniformly broken.

Three decisions inside it:

- **Own body, not the span.** `end_line` runs through subsections, so an H1
  covers every H2 beneath it. Embedding that would copy each child's prose into
  every ancestor's vector and make one H3 edit re-embed the whole chain above
  it. The body stops at the next heading of *any* level; the wide span is still
  what snippet reads and the sparse index use.
- **Fenced code dropped, links flattened.** `[ingest guide](./ingest.md)` →
  `ingest guide`; the URL is not query vocabulary and the path is already an
  `Imports` edge. A section that is *only* a fence gets no docstring and falls
  back to the structural synopsis, which is the honest outcome.
- **Prose files opt out of comment extraction** (`PROSE_EXTS`,
  `storage/ingest.rs`). The scanner from Part 1 §7 treats `#` as a
  line-comment marker — in markdown that is every heading — and its
  string-literal tracking trips on ordinary apostrophes and backticks. What it
  produced for a document was mangled prose in a `Notes:` field.

**Why this asymmetry is correct, not an inconsistency with Part 1 §7.** For a
function, the name and docstring carry the meaning and the body is
implementation. For a document section the body *is* the description and the
heading is a two-word label. The churn argument inverts too: a body edit that
leaves the docstring alone usually is not a change in meaning, whereas a prose
edit always is — so re-embedding it is the correct outcome rather than a cost.

Result on the reported node:

```
Concept: Why bother with a local backend? (why bother with a local backend).
The previous default was a hosted endpoint. That forced every contributor to
spin up an embedding server before any ingest could run, and to manage GPU
memory for that sidecar. Most users just want to index a repo and get a
knowledge graph.. Related: Embedding Backends
```

Also answered the question the report raised — *why did hybrid search find this
anyway?* Two reasons, neither of them "it re-reads files": the sparse channel
indexes `code` at 0.35, and since Part 1 §5 `snippet_for` serves the stored
`code` column. Search does not fan out into filesystem reads on a
freshly-ingested store.

## 9. Caps were invisible

`limits.rs` publishes every cap that shapes what reaches the embedder, with a
stable `id`, `stage`, applicable extensions, a user-facing `effect`, and the
constant it came from. Served on `GET /api/capabilities`; rendered in the
visualization's Chunk tab as *Indexing limits*, marking the caps that
measurably bit **this** node and auto-expanding when one did.

The module holds no cap values of its own — each entry reads the enforcing
constant, with a unit test asserting they still track. `stage`
(index/embed/retrieve) is the useful axis: it says whether changing a cap costs
a re-index, a re-embed, or nothing.

Detecting "reached" is deliberately conservative — a truncation ellipsis, a
`Related:` list returned exactly full, a keyword vector at the dimension cap.
`sparse_dims` was the one cap with no observable trace, which is why
`/api/db/node/:id` now recomputes the vector for the single-row hydrate.

## 10. The description budget follows the model

`SECTION_TEXT_CAP = 1500` was a guess about the model, made in a stage that
cannot see one. It became `SECTION_TEXT_HARD_CAP = 8192` — a bound on
`graph.json`, nothing more — and the real cap moved to `EmbedBudget`
(`limits.rs`), applied in `build_node_text_with_comments`:

```
budget  = clamp(window_tokens × 3.7 − reserve, 500, 8_000)
reserve = 150 (type + name + split name) + MAX_COMMENT_CHARS
```

`bge-small-en-v1.5` (512 tok) → **1,144 chars**; `nomic-embed-text-v1.5` (8,192)
→ the 8,000 ceiling; unknown or remote model → a fixed 1,500, which is what
markdown was hard-coded to, so those models are unchanged.

Two things fall out of it. Switching to a longer-window model now needs a
**re-embed, not a re-index**. And applying it uniformly to every node's
description **fixes the PDF mismatch** flagged earlier in the session: a page is
captured at 8 KB for storage and display, and only what fits the window reaches
the vector, instead of overflowing it silently.

**The reserve deliberately excludes `Related:`.** Position in the template
decides who loses to the tokenizer, and `Related:` comes last — an overflowing
node drops neighbour names, never its description. Reserving for them would
shrink the description to protect the designated casualty. That correction
matters because `MAX_RELATED` moved from 24 to 128 during the session:
`related_advisory()` now reports that at 512 tokens **about zero** neighbour
names fit after the description, so 128 is doing nothing unless the model
changes. Descriptions are unaffected either way.

Adjusting it: `--section-cap`, or `ug config set embed.section_cap`, else
auto-derived. `ug gen` prints the number, its origin, and a warning on
mismatch:

```
▸ Embedding budget: 1144 chars per description (512 token window, derived from the model)
⚠  description budget is 4000 chars but BAAI/bge-small-en-v1.5 reads only ~1894 chars
   (512 tokens) — text past that is dropped by the tokenizer with no marker
```

## 11. A model switch was silently mixing embedding spaces

`ug-meta.json` records the model each store was ingested with, and
`plan_incremental_ingest` refuses to reuse a stored vector when it changed.

The dim guard from Part 1 could not catch this: `bge-small-en-v1.5` and
`all-MiniLM-L6-v2` are **both 384-dimensional**, so a swap between them left
`node_text` identical, the planner called every row unchanged, and the store
ended up holding vectors from two incompatible spaces with nothing to notice.
Demonstrated live — the same swap now reports `13 to embed` where it previously
said `13 unchanged`.

Unrecorded reads as *unknown*, not *mismatched*, so stores written before the
field keep their incremental behaviour rather than re-embedding on every run.

## 12. BM25, without a second index

The keyword channel carried raw term frequency, so `the`, `let` and `return`
counted for as much as `buildSparseKeywordVector`. Survivable when every query
is a distinctive identifier; much less so now that §8 put document prose in the
corpus, because a natural-language query is mostly common words.

Reading the OverGraph source settled the design: sparse scoring is a plain dot
product over posting lists (`sparse_postings.rs`) with no notion of a scoring
model — which is exactly what BM25 needs, because it factorizes into a
document-side factor and a query-side IDF. Store the first as the weight, put
the second in the query vector, and the dot product the engine already computes
*is* BM25. **No engine change, no full-text index, no new dependency.**

`b = 0`, deliberately: length normalization is the only term that couples a
document's weight to the corpus (via `avgdl`), so it would invalidate every
stored vector on any edit and kill incremental re-ingest. With `b = 0` the
document factor is node-local, stored vectors stay valid, and the two effects
that matter — IDF and TF saturation — are both kept. Node spans are also far
more uniform in length than the web documents `b` was designed for.

Two constraints found in the engine source rather than assumed:

- **IDF must be positive.** The *query* vector goes through the same
  `canonicalize_sparse_vector` non-negative validation as a stored one, and
  classic Robertson IDF goes negative past `df > N/2`. So Lucene's smoothed
  `ln(1 + (N − df + 0.5)/(df + 0.5))` is required, not preferred.
- **Fusion is rank-based** (`FusionMode::WeightedRankFusion`), so changing the
  weight *scale* is safe — only ordering matters. That removed the main
  migration risk.

`refresh_sparse_stats` counts `df` over the whole graph in the pass that already
holds every node's text, and writes `ug-sparse-stats.json` beside
`ug-meta.json`. Terms in a single node are omitted and read back as `df = 1` —
they are most of any code vocabulary and share the same near-maximum IDF, so
dropping them roughly halves the sidecar. On the demo store: 13 docs, 138
tracked terms.

**The dimension cap was backwards and got fixed on the way.**
`MAX_SPARSE_DIMS` kept the heaviest *raw frequency* terms — the most repeated
common words. It now ranks by `saturated_tf × idf`. There is a test asserting
`"the"` survives the old selection and is dropped by the new one; that fix may
matter more than BM25 itself.

Fallbacks: no sidecar → plain term frequency, the previous behaviour rather than
an error. Neo4j is unaffected — it has no sparse-vector type and scores its
keyword leg through Lucene, which is already BM25. So this **closes** a gap
between the backends rather than opening one.

## 13. Transparency in the Chunk tab

A document section's `docstring` is a paragraph now, which broke the panel's
layout assumptions and hid what the store actually holds.

- **Long fields collapse** to a one-line preview plus a char count above 180
  chars: the detail panel's `Doc` row, and the Chunk tab's `Description` and
  `Notes from comments`. Previously a 1,500-char doc pushed the tab strip off
  screen.
- **`Notes from comments`** is its own field — different source, own cap.
- **Captured source** shows the `code` column verbatim. Deliberately separate
  from the Preview tab, which reads the same span live from disk: when the two
  disagree the store is stale, and seeing both is the only way to tell.
- **Storage metadata** — vector sizes, embedded-text length, `last_update_at`,
  and the file hash with a live staleness check. Auto-expands as
  `Storage metadata — stale`.

Removed at the end: a click handler on the `N source lines` stat that fetched
`/api/file` and displayed it under the tooltip *"Click to view captured source
content"*. It showed **live disk content labelled as stored content** — the
exact confusion the Preview/Captured-source split exists to remove — so this
took out a mislabel, not just a duplicate.

## What the measurements changed, part 2

- **The binding constraint was never our caps.** `document_page_text` is 8,192
  bytes and the default model reads ~1,894 chars, so three quarters of a dense
  PDF page had been dropped by the tokenizer with no marker anywhere. The fix
  was not a bigger cap; it was making the cap follow the model.
- **`MAX_RELATED = 128` buys nothing at 512 tokens.** The advisory computes
  room for ~0 names. Raising a cap past the window is indistinguishable from
  not raising it, except that it looks like it worked.
- **BM25 needed no new storage engine.** The expected cost was a second index;
  the actual cost was a weighting change on both sides of a dot product the
  engine already computed.

## Loose ends, part 2

- **Existing stores need one `ug gen`** to pick up markdown docstrings, the
  derived budget, the recorded model and the stats sidecar. Nothing breaks
  without it — every new path has a documented fallback — but none of the
  improvements apply until then.
- **`ug-sparse-stats.json` size is unmeasured at scale.** 138 terms on a
  13-node demo says nothing about a 6,000-node repo. Hapax omission should keep
  it to single-digit MB; unverified.
- **BM25 ranking quality is unmeasured.** The tests pin mechanics (IDF ordering,
  saturation, non-negativity, truncation selection), not retrieval quality. No
  before/after on a query set.
- **`MAX_RELATED = 128` vs a 512-token window is unresolved** — the advisory
  reports it, nobody has decided whether to lower the cap or move to an
  8,192-token model.
- **`b = 0` is a deliberate simplification.** Length normalization is the piece
  of BM25 left on the table; adding it needs a full re-ingest and should be
  gated on measurement.
- **`model_token_window` is a hand-maintained table.** Models whose window we
  can't state return `null` and fall back to the fixed budget — correct, but it
  drifts if someone adds a model to `resolve_model` and not to the table.
  MiniLM is deliberately absent rather than guessed at.
- **The Chunk tab's token estimate is ~4 chars/token**, labelled as approximate.
  It is not the model's tokenizer.
